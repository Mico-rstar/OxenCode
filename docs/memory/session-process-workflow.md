## session处理工作流关键点澄清
1. 为什么要先压缩出notes再开启并行处理agent
   - 渐进式披露思想：不要让agent直接处理低密度的大量上下文信息，而是先给agent一个压缩后的精简会话视图，在其中保留关键钩子，不同任务类型的agent根据任务方向再从钩子出发查找关键上下文
   - 成本考量：后续是并行任务，在此阶段进行上下文压缩可以带来乘数级别成本节约

2. 并行agent在工作流中发挥什么角色
   - 将记忆生成，编辑的权限留给agent自行决定，而不是由系统去自主记忆文件
   - 三种不同任务的agent负责不同方向的记忆整理工作，而定义方向的关键是写高质量的系统提示词

3. 为什么用langgraph
   - 避免重复造轮子，复用成熟的抽象
   - langgraph提供了checkpoint持久化，可观测性等机制
   - 可以支持从最后一个成功节点重启任务


## 关键质量约束
### notes中应该包含什么信息
 - 保留关键决策路径，抛弃细节信息。例如调用X工具，得到Y结果
 - 保留关键错误链路，用于给模型反思总结经验
 - 模型调用记忆的信息特别关键，这些链路可以看出记忆是否帮助模型更好完成任务了，过去总结的经验是否还有效
 - 每个notes文件都对应一个histories文件夹中的文件，保留钩子供模型查证原始信息
 - 关键点留关键词钩子，帮助后续agent使用grep命令快速定位原始信息位置
 - 什么是关键点？可能产生新的经验、新的知识、和旧经验/旧知识矛盾、失败点、用户偏好、关键事实、和用户冲突矛盾点、
### Agent系统提示词
#### experience_agent
- 对错误链路进行总结为 case X, do Y的形式，下次遇到类似情况能快速成功
- 对调用experience的链路进行验证，验证过去总结的经验是否在实际环境中起作用了，如果没有，那样总结原因并更新经验
- 寻找新的可复用的范式，经验

#### knowledge_agent
- 总结新的可复用的知识
- 对旧知识在实际链路中的表现进行验证，决定是否更新知识
- 是否将低等级的知识进行更高维度的抽象，概括，总结

#### inner_agent
- user: 提取用户明说的偏好、隐含的偏好、推测用户画像(母语，性格特点，角色，社交圈)、推测用户潜在需求
- self: 在于用户的交互中，新信息获取中，个人知识和经验中，于用户分歧点甚至冲突处，反思和寻找自我，总结成身份定义，自我目标，价值排序，自我偏好，语言特点等维度的描述

### Agent权限限制
- 只使用 read, edit, grep, glob, write 基本工具，工作目录在 memory/  (验证一下5个工具是否够，有没有场景需要bash工具)
- 例如experience只在experience目录有写权限，对memory下的其他目录有读权限，不能跳出memory目录

### Agent上下文管理
需要考量agent工作中上下文超出限制用什么策略，推荐用压缩策略，复用langchain的压缩组件

### workflow
工作流是长链路，通过langgraph持久化支持，确保关键点失败后能够从最后一个成功步骤开始执行
由 restry_session接口触发重试
